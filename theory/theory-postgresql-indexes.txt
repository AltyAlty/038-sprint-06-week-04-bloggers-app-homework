В PostgreSQL таблицы хранятся в виде куч (heap), то есть неупорядоченных наборов записей в файлах файловой системы.

Ключевые идеи того как PostgreSQL хранит данные:
1. Записи лежат в куче без какого-либо порядка без какой-либо сортировки на физическом уровне по умолчанию. Новая запись
просто дописывается туда, где есть место.
2. БД читает данные не построчно и не по одному значению, а страницами (pages, blocks). В PostgreSQL страницы по
умолчанию имеют размер в 8 KB и в одну страницу помещается несколько записей.
3. Единица I/O - это страница, а не запись. Даже если нам нужно одно поле одной записи, с диска все равно поднимается
целая страница.
4. Full scan (Seq Scan) - это последовательный проход по всем страницам таблицы. Чтобы найти запись по условию без
индекса, БД вынуждена читать всю кучу и проверять каждую запись.

/*--------------------------------------------------------------------------------------------------------------------*/

Для операций записи в PostgreSQL используется правило, что при изменении данных физически создаются новые данные
отдельно, а старые данные помечаются как устаревшие, при этом устаревшие данные не удаляются, пока они могут быть
прочитаны хотя бы одной активной транзакцией. Из-за этого правила таблицы набиваются "мертвыми" версиями записей,
которые удаляются либо служебной командой "VACUUM", либо встроенной настройкой "autovacuum".

/*--------------------------------------------------------------------------------------------------------------------*/

PostgreSQL не обновляет запись, перезаписывая ее байты там же, где она лежит, по следующим причинам:
1. Физическая: при изменении длины поля поплыла бы разметка страницы.
2. Логическая: параллельные читатели видели бы несогласованные данные.

/*--------------------------------------------------------------------------------------------------------------------*/

Индексы в PostgreSQL не хранятся в таблицах, а находятся в отдельных файлах.

/*--------------------------------------------------------------------------------------------------------------------*/

PostgreSQL использует в большинстве случаев индексы в формате измененной версии B-Tree - B+Tree.

Главное отличие B-Tree от бинарного дерева поиска (BST) состоит в том, что у B-Tree у узла может быть много потомков, а
не только два, то есть когда у BST узел хранит 1 ключ и имеет до 2 потомков, у B-Tree узел хранит несколько ключей
и имеет столько потомков, сколько ключей + 1.

Одно из свойств B-Tree заключается в том, что оно сбалансировано по высоте, то есть все листья находятся на одной
глубине. Этот баланс поддерживается алгоритмом автоматически при вставке и удалении.

/*--------------------------------------------------------------------------------------------------------------------*/

Селективность - это доля уникальных значений в поле или доля записей, которые пройдут фильтр клаузы "WHERE". Другими
словами, селективность - это отношение уникальных значений к общему числу строк.

Высокая селективность означает, что условие отсеивает почти все, а низкая - условие оставляет много записей. При низкой
селективности PostgreSQL предпочтет прочитать все записи в таблице последовательно, а при высокой - обратиться к
индексам.

/*--------------------------------------------------------------------------------------------------------------------*/

Служебная команда "EXPLAIN" в PostgreSQL показывает предполагаемый план как именно БД собирается выполнить какой-то
запрос, а служебная команда "EXPLAIN ANALYZE" уже реально выполняет запрос, показывая план и фактические метрики. При
анализе можно встретить следующие типы операций:
1. "Seq Scan": последовательное чтение всей таблицы.
2. "Parallel Seq Scan" + "Gather": PostgreSQL запускает параллельно несколько worker'ов, каждый читает свою часть
таблицы как "Seq Scan", а "Gather" собирает их результаты в один поток.
3. "Index Scan": чтение, используя B+Tree.
4. "Index Only Scan" + "Heap Fetches": чтение, используя B+Tree, но без походов в кучу.
5. "Bitmap Heap Scan" + "Bitmap Index Scan": появляется, когда ожидается много строк. В памяти собирается битовая карта
нужных страниц через один или несколько индексов, а затем эти страницы читаются в физическом порядке диска.
Используется, например, когда индекс использует запрос с оператором "OR" - если есть два отдельных индекса ("BitmapOr"),
или если один индекс возвращает много строк, или если есть несколько условий через оператор "AND" по разным индексам
("BitmapAnd").
6. "Sort": пересортировка в памяти или на диске.

/*--------------------------------------------------------------------------------------------------------------------*/

Служебная команда "REINDEX" в PostgreSQL перестраивает индекс с нуля, тем самым убирает неиспользуемы страницы внутри
индекса и восстанавливает поврежденные индексы.

/*--------------------------------------------------------------------------------------------------------------------*/

PostgreSQL при выполнении запроса может сам определить стоит ли идти в таблицу за данными или же получить ее из индекса.

/*--------------------------------------------------------------------------------------------------------------------*/

Индексы, которые не являются PK, называют вторичными (secondary).

/*--------------------------------------------------------------------------------------------------------------------*/

PostgreSQL не создает индексы для FK автоматически, поэтому при необходимости нужно использовать декоратор "@Index()" из
TypeORM при создании FK в сущности.

/*--------------------------------------------------------------------------------------------------------------------*/

В PostgreSQL при помощи клаузы "INCLUDE" можно создавать покрывающие индексы, идея которых состоит в добавлении в индекс
дополнительных колонок, не участвующих в поиске, но часто запрашиваемых вместе с ключом. TypeORM не предоставляет
функционала для работы с клаузой "INCLUDE", поэтому для работы с ней можно использовать миграции, отключая опцию
"synchronize" в параметрах декоратора "@Index()" из TypeORM.

/*--------------------------------------------------------------------------------------------------------------------*/

Порядок условий в клаузе "WHERE" с оператором "AND" не определяет как буквально будет работать PostgreSQL - если условия
будут содержать поля составного индекса, то PostgreSQL это увидит и будет использовать этот индекс. В случае
использования оператора "OR" PostgreSQL сможет использовать составной индекс только если оператор "OR" относится к
первому столбцу составного индекса.

/*--------------------------------------------------------------------------------------------------------------------*/

В PostgreSQL при помощи клаузы "WHERE" можно создавать частичные индексы, идея которых состоит в создании индекса,
берущего не все записи из таблицы, а только прошедшие какое-то условие. Чтобы PostgreSQL использовал частичный индекс,
нужно в запросах указывать условие из этого частичного индекса.

/*--------------------------------------------------------------------------------------------------------------------*/

Кластеризованный (clustered) индекс - это индекс, физический порядок записей в котором совпадает с порядком самой
таблицы, то есть таблица и индекс являются одним целым. В PostgreSQL нет кластеризованных индексов по умолчанию, поэтому
даже PK это просто уникальный вторичный индекс. Но PostgreSQL предоставляет служебную команду "CLUSTER" для разовой
кластеризации, в ходе которой создается новая копия таблицы, физически отсортированная по указанному индексу, заменяется
старая куча новой и перестраиваются все индексы. После такой кластеризации PostgreSQL не поддерживает упорядоченность
автоматически - для этого нужно периодически запускать служебную команду "CLUSTER" заново. При этом нужно помнить, что
служебная команда "CLUSTER" полностью блокирует таблицу на время работы. Для кластеризации на фоне без блокировок можно
использовать отдельные пакеты, например, pg_repack или pg_squeeze.

/*--------------------------------------------------------------------------------------------------------------------*/

В PostgreSQL при помощи клаузы "USING" с аргументом "HASH" можно создавать hash индексы, хранящие хеш значения ключа, по
которому будет идти поиск. Такой индекс используется только в операторе "=". TypeORM не предоставляет функционала для
работы с hash индексами, поэтому для работы с ними можно использовать миграции, отключая опцию "synchronize" в
параметрах декоратора "@Index()" из TypeORM.

/*--------------------------------------------------------------------------------------------------------------------*/

В PostgreSQL при помощи клаузы "USING" с аргументом "GIN" можно создавать Generalized Inverted (GIN) индексы, которые
выглядят как инвертированный индекс: ключ является отдельным токеном внутри значения, а значение - списком строк, где
этот токен встречается. Такие индексы большие и медленно строятся по сравнению с B-Tree, но очень быстро осуществляют
поиск. TypeORM не предоставляет функционала для работы с GIN индексами, поэтому для работы с ними можно использовать
миграции, отключая опцию "synchronize" в параметрах декоратора "@Index()" из TypeORM.

/*--------------------------------------------------------------------------------------------------------------------*/

В PostgreSQL при помощи клаузы "USING" с аргументом "GIST" можно создавать Generalized Search Tree (GiST) индексы. GiST
- это расширяемое дерево, на основе которого строятся индексы для нестандартных типов данных. TypeORM для работы с GiST
индексами предоставляет опцию "spatial" в декораторе "@Index()", но это частный случай для spatial-полей (PostGIS) с
геометрическими или географическими данными, поэтому для работы с такими индексами можно использовать миграции, отключая
опцию "synchronize" в параметрах декоратора "@Index()" из TypeORM.

/*--------------------------------------------------------------------------------------------------------------------*/

В PostgreSQL при помощи клаузы "USING" с аргументом "BRIN" можно создавать Block Range индексы (BRIN), которые хранят
для каждой группы страниц минимум и максимум значения в этой группе. TypeORM не предоставляет функционала для работы с
BRIN, поэтому для работы с ними можно использовать миграции, отключая опцию "synchronize" в параметрах декоратора
"@Index()" из TypeORM.

/*--------------------------------------------------------------------------------------------------------------------*/

В PostgreSQL можно указывать функцию в качестве ключа индекса, тем самым создавая функциональный индекс (expression
index). Функция в индексе обязана быть immutable, так как иначе PostgreSQL не сможет гарантировать, что индекс
согласован с данными и такой индекс просто не будет создан. TypeORM не предоставляет функционала для функций в качестве
ключей индекса, поэтому для этого можно использовать миграции, отключая опцию "synchronize" в параметрах декоратора
"@Index()" из TypeORM.

/*--------------------------------------------------------------------------------------------------------------------*/

Рекомендации по использованию индексов:
1. Стоит использовать составной индекс, когда происходит частый поиск одновременно по двум и более полям.
2. Стоит использовать составной индекс, когда необходимо реализовать проверку на уникальность комбинаций из двух и более
полей.
3. Стоит использовать составной индекс, когда требуется сортировка по двум и более полям.
4. Стоит использовать составной индекс, когда нужно вынести часто запрашиваемые поля, которые являются частями
покрывающего индекса, в один большой индекс.
5. Стоит использовать индекс по полю, когда используется клауза "ORDER BY" в большой таблице, особенно вместе с клаузой
"LIMIT" для пагинации.
6. Стоит использовать два или более отдельных индексов, когда происходит частый поиск с клаузой "WHERE" и оператором
"OR".
7. Стоит использовать частичный индекс, когда происходит частый поиск по большой таблице с каким-то узким условием,
обычно по одному полю.
8. Стоит использовать hash индекс, когда нужен только поиск по точному равенству и использование B-Tree в таком случае
будет избыточно, например, когда значения в таблице длинные и сравнивать их по байтам дороже, чем хешировать.
9. Стоит использовать GIN индексы, когда происходит поиск по JSONB, по элементам массива или по словам из текста.
10. Стоит использовать GiST индексы, когда происходит поиск по геометрическим данным, по диапазонам или по данным с
ограничениями и пересечением. Также GiST индексы будут быстрее для записи данных в формате JSONB, когда GIN - для
чтения.
11. Стоит использовать BRIN, когда таблица содержит большое количество данных и эти данные на диске физически
упорядочены, например, таблица, в которой записи упорядочены по дате создания. В таком случае индекс позволит отсекать
большое количество записей за короткий промежуток времени.
12. Стоит использовать функциональный индекс, когда нужно форматирование данных на лету, например, приведение email к
одному регистру или удаление пробелов по бокам у строкового значения.
13. Стоит использовать функциональный индекс, когда, например, нужен поиск по большим текстам. В таком случае стоит
использовать хеширование при помощи функции "md5()".

/*--------------------------------------------------------------------------------------------------------------------*/

Рекомендации когда лучше не использовать индексы:
1. Когда таблица маленькая и не растет быстро, например, меньше 1000 записей.
2. Когда у поля таблицы низкая селективность.
3. Когда индекс создается "на всякий случай" без реальной необходимости. PostgreSQL позволяет делать запросы для
получения статистики использования каждого индекса, чтобы находить "мертвые" индексы.
4. Когда в таблице происходит намного больше операций записи, чем чтения.
5. Когда поле в таблице часто обновляется.

/*--------------------------------------------------------------------------------------------------------------------*/

Использование формата UUIDv4 для создания PK нежелательно, так как формат UUIDv4 является полностью случайным
128-битным ключом, при каждой вставке попадающим в произвольное место B-Tree PK-индекса, а не в одну правую страницу
индекса, и поэтому часто создающим разветвление (split) B-Tree в случайных местах по всему индексу. В PostgreSQL это
приводит к тому, что индексы начинают занимать больше места, чем объективно нужно для текущего объема полезных данных.
Так же сильно увеличивается размер журналов (Write-Ahead Log), в которых PostgreSQL сначала фиксирует все то, что
планирует изменить на диске.

Несколько альтернатив формату UUIDv4:
1. UUIDv7: первые 48 бит - это миллисекундная отметка времени. Сохраняется свойство уникальности UUID, но ключи
монотонно растут во времени. Вставки идут в правый лист B-Tree, что не провоцирует случайных splits.
2. ULID: примерно то же, что и формат UUIDv7, только 26-символьный base32, time-sortable.
3. KSUID (Segment): 27-символьный, тоже с отметкой времени в начале.

Для других форматов можно использовать отдельные пакеты или встроенную функцию "uuidv7()" в PostgreSQL 18 для генерации
значений в формате UUIDv7.
